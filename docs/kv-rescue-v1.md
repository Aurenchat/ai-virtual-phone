# Float KV Rescue v1

`/float-kv-rescue` is a standalone Response. It loads the installed project Dexie
distribution (generated by `scripts/build-kv-rescue-dexie.mjs`) and native rescue
modules. No root layout, MainApp, kv-db, plugins, hydration, or schedulers load.

The readonly reader discovers existing schema dynamically, verifies native
version 10 (Dexie `version(1)`) and only `entries` with primary key `key`, without
indexes or auto-increment. Its IDB adapter disallows explicit-version opens,
intercepts/aborts upgrade events, and forbids deletion. This is necessary because
Dexie's automatic missing-database handling calls deleteDatabase and declared
schema handling may repair/bump versions. The global databases() API is masked
only during isolated opening so Dexie's Safari readiness polling cannot hang.
Every operation has a 15-second deadline, aborts its active readonly transaction,
and closes on timeout. Late events cannot reopen a database or report success.

After an explicit bounded key/one-row diagnostic succeeds, KV-only preflight
reads primary keys in pages of 32 and values individually. Value cap is 32 Mi
UTF-16 characters; an oversize item stops rather than silently dropping data.
No whole-store toArray/getAll/value list is used. Inventory includes each
canonical KV source, unchanged module/source identities, and physical record
coverage. Cloud credentials are included via the existing settings source 999;
cloud backup run state is explicitly excluded. Any other unowned key is an error.

Value strings are preserved exactly, including JSON whitespace, escapes, and
embedded media. The ordinary v2 media serializer reparses JSON and would lose
string identity. KV rescue therefore uses v2's legal raw-string representation,
escaping only 64 Ki-character slices to a JSON Blob. It never decodes embedded
media. All existing rescue modes retain their existing media serializer. STORE
ZIP, part size limits, SHA, download/share confirmation and file verifier are
shared. Content fingerprints hash bounded UTF-16 chunks and maintain per-source
chains; inventory, resumed state, actual exported chains and final inventory must
agree. Same-count value edits invalidate resume/finish. Checkpoint contains only
metadata/hashes/one last key under `float_kv_rescue_checkpoint_v1`.

## Hydration fallback boundary

`MainApp` awaits hydrateKvDb, checks isKvHydrated, then calls hydrateChatStorage.
However hydrateKvDb itself does unbounded toArray and then may bulkPut migrated
localStorage values and remove legacy keys. Root ChatPluginBootstrap runs before
MainApp's effect completes; an early interception would require a root-wide boot
gate plus separation of hydration from migration. This release leaves that boot
path and its failure protection intact; it does not claim boot hydration readonly.

The minimum fallback is an explicit Data Management button in an already hydrated
Float. It verifies isKvHydrated, opens the standalone cache window, hands over
primitive key/value strings returned by kvEntries into that window's own Map,
then unloads the old Float document by navigation to a standalone receipt page.
No parent callback/objects are retained in the cache reader; no new hydration or
migration runs. Before handoff, the existing app's normal runtime is already
active; the rescue button itself performs no database writes. There is no claim
that that runtime or cache exactly equals the durable DB. No URL starts normal
Float hydration in a rescue page; no fallback can bypass hydration failure.

Cache mode is `kv-cache-snapshot`, permanently complete=false, with
snapshotComplete only when cache counts/content reconcile. Its special verifier
verifies files only and returns complete=false/snapshotVerified=true. The normal
backup verifier rejects cache sets, even if complete is tampered true. Cache
reload needs another explicit handoff and matching fingerprint to resume. No
fallback automatically unlocks migration or claims a persistent COMPLETE.

Real iPhone compatibility remains unverified until the user runs the new bounded
Dexie diagnostic and copies its metadata-only result. Chromium fixture/import
tests are algorithm/safety evidence, not proof the WebKit hang is resolved.
